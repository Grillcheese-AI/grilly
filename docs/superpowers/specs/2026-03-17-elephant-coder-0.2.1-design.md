# elephant-coder 0.2.1 — "Invisible Memory" Design Spec

**Date:** 2026-03-17
**Author:** grillcheese + Claude
**Plugin:** elephant-coder (grilly-plugins marketplace)
**Upgrade from:** 0.2.0 → 0.2.1

## Summary

elephant-coder 0.2.1 transforms from a manual toolkit into invisible infrastructure. Claude automatically has persistent project memory, cross-project framework knowledge, scope discipline, and validated planning — without the user or Claude needing to explicitly call tools.

### Goals

1. **Performance** — Batch operations, single index call, SQLite-only fallback
2. **Configurable limits** — Settings file + MCP tool for runtime config
3. **Invisible to Claude** — Hooks inject knowledge automatically; tools are escape hatches, not the primary interface
4. **Cross-project framework knowledge** — Grilly API follows you to new projects
5. **Cross-project bug fixing** — Framework bugs discovered downstream auto-generate PRs
6. **File link graph** — Resolved import/include/shader links between files
7. **Persistent task list** — Survives across sessions, auto-updated
8. **Scope guard** — No feature creep, enforced testing, change requests for out-of-scope work
9. **Idea validation** — Research-grounded planning with confidence thresholds
10. **External model validation** — Anti-bias check via OpenRouter, adversarial review from a different model
11. **Research engine & creative notes** — Paper search, persistent notes, cross-reference sparks for novel ideas

## Section 1: Automatic Knowledge Injection

### Philosophy

The plugin shifts from "tools Claude calls" to "hooks that inject knowledge automatically." Claude starts every session already oriented — no exploration needed.

### SessionStart Hook (prompt type)

Runs automatically when a session begins:

1. Calls `index_all()` internally (one call, all patterns, batch upserts)
2. Checks for project objectives — if none, triggers Objective Onboarding (Section 8)
3. Generates a **Project Mental Model** from indexed memories + file link graph
4. Loads task list and active change requests
5. Loads global knowledge (framework references if applicable)
6. Injects everything into Claude's context

### Project Mental Model

Auto-generated, not a static file. Example output for grilly:

```
## Project Mental Model (auto-generated by elephant-coder)

### What This Project Is
Grilly: GPU-accelerated neural network framework using Vulkan compute shaders.
PyTorch-like API, runs on any GPU (AMD/NVIDIA/Intel) via Vulkan.

### Architecture Layers (call direction: top -> bottom)
  utils/ (DataLoader, HuggingFaceBridge, VulkanTensor)
    | uses
  optim/ (Adam, AdamW, SGD, AutoHypergradientAdamW)
    | uses
  nn/ (Module subclasses: Linear, Conv2d, SNN neurons, Transformers, LoRA)
    | uses
  functional/ (stateless wrappers -> instantiate VulkanCompute)
    | calls
  backend/ (VulkanCompute -> pipelines -> core -> shader dispatch)
    | loads
  shaders/ (137+ GLSL compute shaders -> compiled SPIR-V in spv/)

### Key Patterns
- Entry point: grilly.Compute() -> namespaced ops (backend.snn.lif_step(), etc.)
- All data: np.float32 numpy arrays, GPU upload/download transparent
- Adding a new op: write GLSL shader -> compile to SPIR-V -> add backend method -> expose in functional/

### Most Connected Files (hub nodes)
- backend/compute.py (imported by 23 files -- composes all op modules)
- nn/module.py (imported by 18 files -- base Module class)
- backend/core.py (imported by 12 files -- Vulkan device/buffer management)

### Recently Changed (last 7 days)
- backend/cubemind.py -- updated bindings
- backend/block_ops.py -- fixed bindings
```

Generated by analyzing:
- Module-level summaries from indexed memories
- Resolved import graph (file_links table)
- Hub detection (files with most inbound links = architectural pillars)
- Git recent changes
- Pattern detection from class hierarchies and dependency chains

### PreToolUse:Read Hook (prompt type)

Before Claude reads any file, auto-injects that file's memories:
- Symbol summaries (functions, classes)
- Dependencies (what this file imports, what imports it — resolved paths)
- Staleness status
- Related tasks

Claude reads the file with context already loaded.

### PostToolUse:Edit Hook (command type, silent)

Re-indexes the edited file immediately via background shell command. No prompt — just keeps the index fresh. Replaces the current reminder-style hook.

### PostToolUse:Write Hook (command type, silent)

Same as Edit — indexes newly created files silently.

## Section 2: Cross-Project Bug Workflow

### Scenario

User is building `new-ml-project`, Claude writes grilly code, hits a bug where `grilly.nn.Conv2d` crashes on certain input shapes. The traceback points into grilly source.

### Automated Flow

1. **Bug origin detection** — Global knowledge stores grilly source paths. When a traceback includes files under the grilly repo path, it's tagged as a framework bug, not user code.

2. **Context loading** — elephant-coder pulls relevant grilly memories: the affected class, its dependencies, the backend shader it dispatches to, recent changes.

3. **Worktree + branch** — Claude creates a git worktree in the grilly repo (e.g., `fix/conv2d-input-shape`), makes the fix with full grilly project context.

4. **PR creation** — Opens a PR on grilly's GitHub with the fix, referencing the bug discovered in the downstream project.

5. **Resume** — Claude returns to the current project, reports the fix PR, offers to install grilly from the fix branch to unblock work.

### Requirements

- Global knowledge stores framework repo paths and GitHub remote
- `auto_fix_prs` must be `true` in settings (default: false)
- Only triggers when a traceback clearly points to framework source
- Requires `gh` CLI for PR creation

## Section 3: Framework Detection

### Auto-Detection Logic (SessionStart)

```
Is grilly installed?
  Check 1: "grilly" in pyproject.toml/requirements.txt dependencies
  Check 2: `import grilly` succeeds
  Check 3: Project IS grilly (has backend/compute.py + shaders/)
  Any match -> activate framework features
```

### When Grilly IS Detected

- Load grilly global knowledge (API map, patterns, idioms)
- Enable shader-to-Python linking
- Enable cross-project bug-to-PR workflow
- Inject grilly mental model into session context
- "What broke?" includes shader change impact

### When Grilly is NOT Detected

Full general-purpose memory still works:
- Indexing, search, file links, project overview
- Pattern learning, cross-session continuity
- Benchmark memory, architecture guard
- Framework features are generic — any project can be exported as a framework

### Two-Layer Memory Architecture

**Layer 1: Project Memory** (existing, per-project)
- SQLite database at `~/.elephant-coder/{project_hash}/memories.db`
- Symbols, file links, project mental model, tasks
- Scoped to one repo

**Layer 2: Global Knowledge** (new)
- SQLite database at `~/.elephant-coder/global/knowledge.db`
- Framework references, API mappings, user preferences, session summaries
- Follows user across ALL projects
- Auto-generated from deeply-indexed projects

### Global Framework Knowledge Capsule

Auto-generated when a framework-shaped project is indexed:

```
## grilly Framework Reference (auto-generated, global)

### torch -> grilly Migration Map
torch.nn.Linear        -> grilly.nn.Linear
torch.nn.Conv2d        -> grilly.nn.Conv2d
torch.optim.Adam       -> grilly.optim.Adam
torch.nn.functional.relu -> grilly.functional.relu
torch.Tensor           -> np.ndarray (float32)
torch.device("cuda")   -> grilly.Compute() (auto-selects Vulkan GPU)

### Quick Start Pattern
import numpy as np
from grilly import Compute
from grilly.nn import Linear, Module
from grilly.optim import Adam

### Key Differences from PyTorch
- No CUDA dependency -- Vulkan compute shaders on any GPU
- Data is always np.float32 numpy arrays, not torch.Tensor
- grilly.Compute() replaces torch.device -- single entry point
- Shaders are GLSL -> SPIR-V, not CUDA kernels
```

### Framework Export

- Auto-extracted when indexing a framework-shaped project (has `__init__.py` exports, `nn/`, `optim/`, etc.)
- `update_settings()` tool lets Claude mark a project as "framework -- export to global knowledge"
- Can be manually triggered via `/ec:export-framework`
- Generic: works for grilly, Django, React component libraries, etc.

## Section 4: Redis Optional, SQLite Fallback

### Current Behavior (0.2.0)

`RedisCache.__init__` raises `RuntimeError` if Redis is unavailable. Server crashes.

### New Behavior (0.2.1)

- SQLite is the source of truth — always works, zero setup
- Redis is a pure performance cache — speeds up repeated queries
- If Redis is available: write-through cache, FTS cache, file sets
- If Redis is unavailable: log one info message, continue with SQLite only
- No crash, no error, no degraded functionality

### Implementation

```python
# RedisCache.__init__ -- graceful fallback
try:
    self._r = redis_lib.from_url(redis_url, decode_responses=True)
    self._r.ping()
    self._available = True
    logger.info("Redis cache connected: %s", redis_url)
except Exception:
    self._available = False
    logger.info("Redis not available -- using SQLite only (this is fine)")
```

All `RedisCache` methods already check `self._available` — no other changes needed. Just remove the `raise RuntimeError`.

### Settings

```yaml
redis_url: "redis://localhost:6380"  # or null/omitted to skip
redis_ttl: 31536000  # 1 year default
```

## Section 5: Batch Performance

### Problem

Current indexing: one `INSERT OR REPLACE` + FTS delete/insert + Redis put per symbol.
For 62k symbols: ~186k individual SQL operations.

The `/index` command fires 14 parallel MCP round-trips at session start.

### Solutions

#### `upsert_batch(entries: list[MemoryEntry])` method

- Wraps all entries from one file in a single SQLite transaction
- Batch FTS updates inside the same transaction
- Single Redis pipeline for all entries in one `pipeline.execute()` call
- Expected speedup: 5-10x for initial indexing

#### `index_all()` replaces 14 separate tool calls

- One internal function, loops all supported patterns
- Returns single combined result
- SessionStart hook calls this once, silently
- Still exposed as MCP tool for manual use

#### Consolidation Improvements

- Evict stale entries first before touching relevant ones
- Configurable `max_memories` from settings file (default 50k)
- Better eviction: consider dependency graph — don't evict hub nodes

## Section 6: File Link Graph

### New SQLite Table

```sql
CREATE TABLE IF NOT EXISTS file_links (
    source_path TEXT NOT NULL,
    target_path TEXT NOT NULL,
    link_type TEXT NOT NULL,  -- "import", "include", "shader_dispatch"
    symbol_name TEXT,         -- specific symbol if known
    PRIMARY KEY (source_path, target_path, link_type)
);

CREATE INDEX IF NOT EXISTS idx_links_target
    ON file_links(target_path);
CREATE INDEX IF NOT EXISTS idx_links_source
    ON file_links(source_path);
```

### Population During Indexing

- **Python:** Resolve `from grilly.nn import Linear` to `nn/linear.py` using sys.path logic
- **C/C++:** Resolve `#include "core.h"` to `backend/core.h` using include path search
- **GLSL shaders:** Detect `load_shader("conv2d_gemm")` patterns in Python, link to `shaders/conv2d_gemm.glsl`
- **Fallback:** String-match on module names (existing behavior, for languages without full resolution)

### Powers

- `project_overview()` hub detection — most inbound links = architectural pillars
- `get_dependencies()` returns actual resolved file paths
- "What broke?" traces impact through the graph
- Architecture guard checks for layer violations
- Shader-to-Python linking for grilly

## Section 8: Scope Guard & Change Management

### The Rule

Every code change must trace back to an active task. No task = no change.

### Objective Onboarding

**Triggers at SessionStart if no objectives are set.**

Claude is prompted to ask the user for the project's main objective. The objective must be:
- **Specific** (not "make it better")
- **Actionable** (can be broken into tasks)
- **Measurable** (you know when it's done)

If the user gives something vague, Claude asks follow-up questions until the objective is concrete.

Examples:
- Vague: "build a web app" -> Follow-up: "What does the app do? Who uses it? What's the MVP?"
- Vague: "improve grilly" -> Follow-up: "Which part? Performance of what op? Compatibility with what?"
- Good: "Implement flash attention v2 with backward pass, matching PyTorch API, benchmarked against torch on A100"

**Onboarding blocks all other work.** Claude cannot start editing files until objectives are set. This prevents "just start coding and figure it out."

Objectives can be updated via `update_settings()` but changes trigger a Change Request for paper trail.

### PreToolUse:Edit/Write Scope Check (prompt type)

Before Claude edits or creates any file, the hook checks:

1. Is there an active (`in_progress`) task that covers this change?
2. Does this file fall within that task's scope?
3. Is this change aligned with the project's stated objectives?

If NO to any:
- Block the edit
- Prompt Claude to either pick an existing task or write a Change Request

### Change Request Format

```
## Change Request #CR-003
Date: 2026-03-17
Triggered by: Claude attempted to refactor backend/core.py
              while working on Task #7 (fix Conv2d GEMM path)

### What Claude Wanted to Do
Refactor VulkanCompute.__init__ to split device selection into
a separate method.

### Why
Encountered during Conv2d fix -- device init code is tangled
with the fix area.

### Impact Assessment
- Files affected: backend/core.py, backend/compute.py
- Dependents: 23 files import from core.py
- Risk: HIGH -- core initialization path

### Decision Required
- [ ] Approve -- add as new task, do it now
- [ ] Defer -- add to backlog, stay on current task
- [ ] Reject -- not needed, continue without it
```

Stored in `~/.elephant-coder/{project_hash}/change_requests/`. Claude cannot proceed with out-of-scope work until the user approves.

### Auto-Test Enforcement (PostToolUse:Edit prompt)

After any edit:
```
"You just modified {file}. Run the relevant tests before continuing.
Do not move to the next task until tests pass."
```

## Section 9: Idea Validation Loop

### When It Triggers

After objectives are set and before any task gets marked `in_progress`, every planned approach goes through validation.

### The Validation Loop

```
For each task/approach in the plan:

1. RESEARCH
   - Search elephant-coder memories for prior attempts
   - Web search for known issues with the approach
   - Check framework docs (context7, HF docs, etc.)
   - Look for "X doesn't work because..." patterns

2. ASSESS CONFIDENCE
   Rate: "What's the probability this approach works?"

   Evidence sources:
   - Prior session logs (did we try this before and fail?)
   - Known limitations in dependencies
   - API compatibility issues
   - Hardware/platform constraints
   - Community reports of similar attempts

3. DECISION
   >= 95% confidence -> PROCEED, log reasoning
   70-94%            -> FLAG risk, propose mitigation, re-assess
   < 70%             -> REJECT, auto-generate alternative approach
                        Loop back to step 1 with new approach

4. LOG
   Store validation result in task metadata:
   {
     "approach": "Use SPIR-V subgroup ops for reduction",
     "confidence": 0.97,
     "evidence": [
       "Vulkan 1.1+ guarantees subgroup support",
       "Tested in shader_test_suite session 2026-03-10",
       "AMD/NVIDIA/Intel all support basic subgroup ops"
     ],
     "risks": ["Intel Arc has different subgroup size"],
     "fallback": "Use shared memory reduction if subgroup fails"
   }
```

### Example

```
Task: "Add bfloat16 support to grilly"

RESEARCH:
- Vulkan has no native bfloat16 -> need shader emulation
- Prior session 2026-02-20 attempted this, hit precision issues
- Community: VK_KHR_16bit_storage only covers float16, not bfloat16

CONFIDENCE: 40% -- no native Vulkan support, emulation too slow

AUTO-PIVOT:
Alternative: "Add float16 support using VK_KHR_16bit_storage"
CONFIDENCE: 92%

FLAG: 92% < 95%. Risk: Intel iGPU may not support the extension.
Mitigation: Runtime capability check, fallback to float32.

RE-ASSESS with mitigation: 96% -> PROCEED
```

### Change Requests from Validation

If a planned task fails validation (<70%), elephant-coder auto-generates a CR:

```
## Change Request #CR-004 -- Approach Rejected by Validation

Task: Add bfloat16 support
Original approach: Vulkan shader emulation
Confidence: 40%
Reason: No native Vulkan bfloat16, emulation too slow

Proposed alternative: float16 via VK_KHR_16bit_storage
New confidence: 96%

Decision Required:
- [ ] Approve alternative
- [ ] Research further
- [ ] Drop the task entirely
```

## Section 10: External Model Validation (Anti-Bias Check)

### Problem

Claude has blind spots. It can be overly optimistic about its own plans, miss edge cases, or converge on a solution because it "feels right" rather than because it's correct. A single model reviewing its own work is inherently biased.

### Solution: OpenRouter Second Opinion

Before a plan or major approach is finalized, elephant-coder can call an external model via OpenRouter to challenge the plan. This is opt-in and configurable.

### Flow

```
Plan finalized by Claude
  |
  v
External Validation enabled in settings?
  |-- NO -> skip, proceed normally
  |-- YES ->
        |
        v
      Compose review prompt:
        - Project objectives
        - Proposed plan/approach
        - Evidence and confidence scores
        - "Find flaws. Be adversarial. What will go wrong?"
        |
        v
      Call OpenRouter API with selected model
        |
        v
      Parse response:
        |-- No major issues -> log agreement, proceed
        |-- Issues found ->
              |
              v
            Present to user:
              "External reviewer (Gemini 2.5 Pro) flagged:
               1. The file_links resolver won't handle circular
                  imports in Python -- need cycle detection.
               2. Batch upsert with 1000+ entries may hit SQLite
                  max variable limit (999 per statement).

               Do you want to:
               - [ ] Address these before proceeding
               - [ ] Acknowledge and proceed anyway
               - [ ] Request another review with a different model"
```

### OpenRouter Integration

```python
# research_engine.py — external validation

import httpx

async def get_external_review(
    plan: str,
    objectives: list[str],
    evidence: list[str],
    api_key: str,
    model: str | None = None,
) -> dict:
    """Call OpenRouter for an adversarial review of the plan."""

    # Claude picks the model based on the task domain
    # Default: a strong reasoning model that's different from Claude
    if model is None:
        model = "google/gemini-2.5-pro"

    prompt = f"""You are reviewing a software implementation plan.
Be adversarial — your job is to find flaws, missed edge cases,
incorrect assumptions, and things that will fail in practice.

## Project Objectives
{chr(10).join(f'- {o}' for o in objectives)}

## Proposed Plan
{plan}

## Evidence/Research
{chr(10).join(f'- {e}' for e in evidence)}

## Your Review
For each issue found, rate severity (critical/major/minor) and
explain WHY it's a problem and WHAT would fix it. If the plan
is solid, say so — don't invent problems."""

    response = httpx.post(
        "https://openrouter.ai/api/v1/chat/completions",
        headers={
            "Authorization": f"Bearer {api_key}",
            "Content-Type": "application/json",
        },
        json={
            "model": model,
            "messages": [{"role": "user", "content": prompt}],
            "temperature": 0.3,  # focused, not creative
        },
        timeout=60,
    )

    result = response.json()
    review_text = result["choices"][0]["message"]["content"]
    model_used = result.get("model", model)

    return {
        "model": model_used,
        "review": review_text,
        "raw_response": result,
    }
```

### Model: google/gemini-3.1-flash-lite-preview

The external reviewer is **Gemini 3.1 Flash Lite** via OpenRouter. This is a fixed choice, not configurable per task — the reviewer must be consistent and independent.

**Why this model:**
- Fast and cheap — reviews shouldn't cost more than the work itself
- Different architecture from Claude — catches different blind spots
- Good enough reasoning for adversarial review without being overkill

### Roles

The external model serves two roles:

**1. Plan Validator** (during idea validation, Section 9)
- Reviews proposed approaches before work begins
- Adversarial: "find flaws, missed edge cases, incorrect assumptions"
- Blocks work if critical issues found

**2. Independent Auditor** (during and after implementation)
- Reviews completed work against the original plan
- Checks: "Did Claude actually do what was planned? Did it drift?"
- Checks: "Are there bugs, security issues, or missed requirements?"
- Runs automatically after each major task completion
- Audit results stored in `~/.elephant-coder/{hash}/audits/`

### Audit Flow

```
Task marked completed by Claude
  |
  v
Auto-trigger audit (if enabled):
  |
  v
Compose audit prompt:
  - Original task description and acceptance criteria
  - Files changed (git diff)
  - Test results
  - "Did the implementation match the plan?
     What was missed? What was added that shouldn't be?"
  |
  v
Call Gemini 3.1 Flash Lite via OpenRouter
  |
  v
Parse response:
  |-- Clean audit -> log, proceed to next task
  |-- Issues found ->
        Present to user:
          "Auditor (Gemini 3.1 Flash Lite) flagged:
           1. Task said 'batch upsert' but implementation
              still calls upsert() in a loop — no actual
              batching.
           2. New test coverage only covers happy path —
              no edge case tests for empty input.

           - [ ] Fix before moving on
           - [ ] Acknowledge, fix later
           - [ ] Dismiss (false positive)"
```

### Audit Report Format

```json
{
  "task_id": "T-005",
  "auditor": "google/gemini-3.1-flash-lite-preview",
  "timestamp": "2026-03-17T15:30:00Z",
  "verdict": "issues_found",
  "issues": [
    {
      "severity": "major",
      "description": "Batch upsert not actually implemented",
      "expected": "Single transaction for all entries",
      "actual": "Loop calling upsert() individually",
      "file": "memory_store.py",
      "recommendation": "Use executemany() inside a transaction"
    }
  ],
  "plan_adherence": 0.85,
  "scope_drift": false
}

### Settings

```yaml
---
external_validation:
  enabled: false  # opt-in
  openrouter_api_key: "sk-or-..."  # or env: OPENROUTER_API_KEY
  model: "google/gemini-3.1-flash-lite-preview"  # fixed reviewer
  validate_plans: true  # review plans before work starts
  audit_completed_tasks: true  # audit after each task completion
  require_approval_on_issues: true  # block until user decides
---
```

### MCP Tools

- `get_external_review(plan, context)` — Claude calls this for plan validation. Also available manually for ad-hoc second opinions.
- `request_audit(task_id)` — Triggers an independent audit of a completed task. Auto-called when a task is marked completed (if `audit_completed_tasks` is true).

### Privacy Note

The review prompt only sends: objectives, plan text, and evidence. No source code, file contents, or proprietary information is sent to OpenRouter unless explicitly included in the plan text. The settings file documents this.

## Section 11: Research Engine & Creative Notes

### Paper Research Integration

During idea validation (Section 9) and general exploration, Claude automatically searches for relevant academic papers and technical resources:

**Research sources:**
- Web search for papers, blog posts, benchmarks
- Hugging Face paper search (via HF MCP tools)
- arXiv references from indexed code comments and docstrings
- Context7 for library documentation

**Auto-triggered during:**
- Idea validation loop (Section 9 step 1: RESEARCH)
- When Claude encounters an unfamiliar algorithm or technique in the codebase
- When the user asks about a new approach or feature

### Research Notes (Global Knowledge)

Claude can take notes on interesting findings — stored as `note` entries in the global knowledge store, not project-scoped:

```json
{
  "kind": "research_note",
  "topic": "Sparse attention via locality-sensitive hashing",
  "source": "arxiv:2106.04554 (Reformer)",
  "summary": "LSH attention reduces O(n^2) to O(n log n). Could replace flash_attention for very long sequences. Requires custom hash kernel.",
  "tags": ["attention", "performance", "long-context"],
  "relevance_to": ["grilly/backend/attention.py", "grilly/shaders/flash_attention2.glsl"],
  "discovered_in_session": "2026-03-17",
  "actionable": true,
  "potential_task": "Implement LSH attention as alternative to flash_attention2 for seq_len > 8192"
}
```

**MCP tools:**
- `take_note(topic, summary, tags, source)` — Claude saves an interesting finding
- `recall_notes(query, tags)` — Search saved research notes
- Notes are auto-injected at SessionStart if they're relevant to active tasks

### Cross-Reference Engine (Creative Ideation)

The real power: elephant-coder periodically cross-references notes to surface **novel combinations**. This runs during `project_overview()` generation:

```
Cross-Reference Algorithm:
1. Load all research notes with overlapping tags
2. For each pair of notes, check:
   - Do they solve related problems from different angles?
   - Could combining them create something new?
   - Does one note's solution address another note's limitation?
3. Generate "spark" suggestions:

## Creative Sparks (auto-generated)

[Spark #1] Notes "LSH attention" + "Vulkan subgroup operations"
  -> LSH hash computation maps naturally to subgroup shuffle ops.
     Could implement O(n log n) attention entirely in one shader
     pass using subgroup-level hash buckets.
  Confidence: 78% -- needs prototype

[Spark #2] Notes "Capsule networks for routing" + "MoE sparse gating"
  -> Capsule agreement routing is mathematically similar to MoE
     top-k gating. Could unify into a single differentiable
     routing primitive that handles both capsule and MoE patterns.
  Confidence: 85% -- both patterns already in grilly
```

**Sparks are:**
- Stored as special research notes with `kind: "spark"`
- Surfaced to the user when relevant to current work
- Can be promoted to tasks if the user approves
- Validated through the idea validation loop (Section 9) before becoming tasks

### Session-Level Research Behavior

Claude doesn't wait to be asked — during normal work, if it encounters something interesting:

1. **While reading code:** "This capsule routing is similar to the Transformer routing paper I found earlier" — takes a note linking them
2. **While fixing bugs:** "This numerical instability is a known issue in float16 attention — Paper X has a solution" — takes a note with the fix approach
3. **While validating ideas:** Research findings are automatically saved as notes, not thrown away after validation

The notes build up over time into a **personal research library** that makes Claude increasingly creative and well-informed across sessions.

## Additional Features

### Pattern Learning

When Claude writes code the user accepts, elephant-coder stores it as an "idiom" in global knowledge. Over sessions, Claude learns preferred coding patterns. E.g., "user always initializes VulkanCompute with gpu_mode(True)" or "user prefers AdamW over Adam."

### "What Broke?" Diff Tool

After `git pull` or merge, diffs memories against new code and reports semantic changes: "The flash_attention2 function now takes a causal_mask parameter -- 4 callers need updating." Exposed as MCP tool `what_broke()`.

### Shader-to-Python Linking

Grilly-specific: links each GLSL shader to the Python backend method that dispatches it via the file_links table with `link_type = "shader_dispatch"`. When a shader changes, Claude knows which Python code is affected.

### Cross-Session Continuity

Stores session summaries in global knowledge. Next SessionStart loads: "Last session you were fixing Conv2d GEMM path -- the GPU transpose kernel was the blocker."

### Architecture Guard

PostToolUse:Write hook checks the file link graph for layer violations. If Claude writes code where `backend/` imports from `nn/` (wrong dependency direction), warns before the pattern sticks.

### Benchmark Memory

Stores benchmark results in project memory. Auto-compares against historical results to detect regressions across sessions.
